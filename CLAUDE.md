# local_helper

Збірка дрібних консольних скриптів (Python, а також PowerShell і Bash) для швидких особистих задач
(обробка файлів, конвертації, перейменування, парсинг тощо) і лаунчер `local_helper`
(аліас `lh`), через який вони запускаються. Це не продукт і не бібліотека: кожен
тул — окремий, самодостатній інструмент.

Повний посібник (встановлення, команди, TUI, `add`, контракт тулу) — у [GUIDE.md](GUIDE.md).
Розділ 5 «Контракт тулу» і чекліст звідти обов'язкові для кожного нового тулу.
Створення тулу чи підключення існуючого скрипта — через скіл `/lh-tool`
([.claude/skills/lh-tool/SKILL.md](.claude/skills/lh-tool/SKILL.md)): там порядок дій і
контракти для `.ps1`/`.sh`.
Коли додаєш, перейменовуєш чи видаляєш вбудований тул, онови таблицю «Тули» в
[README.md](README.md). Якщо змінюєш команди чи клавіші лаунчера, онови `GUIDE.md`.

## Середовище

- ОС: Windows 11, основна оболонка — PowerShell.
- Python: **3.10** (`python`). Не використовувати можливості 3.11+
  (`tomllib`, `ExceptionGroup`, `typing.Self`, `except*` тощо).
- `uv` не встановлений. Залежності ставляться в спільне `.venv` у корені командою
  `local_helper setup`. Тести й тули запускати Python'ом з `.venv`:
  `.\.venv\Scripts\python.exe`.
- PowerShell 7 (`pwsh`) і Git Bash встановлені; `C:\Windows\System32ash.exe` — це WSL без
  дистрибутивів, його не використовувати (лаунчер шукає Git Bash сам: `find_bash`).

## Структура

```
Diferrent Tools/
├── local_helper.py       # лаунчер і всі текстові команди (тільки stdlib)
├── local_helper_tui.py   # повноекранний TUI на Textual (`lh` без аргументів)
├── local_helper.cmd      # обгортки для PATH; запускають Python з .venv, якщо він є
├── lh.cmd
├── lh                    # та сама обгортка для Git Bash (без розширення, LF)
├── install.ps1           # додає папку в PATH користувача
├── registry.json         # підключені командою `add` зовнішні тули (шляхи на цьому ПК, не в git)
├── groups.json           # групи тулів: ім'я тулу → група (в git)
├── workdirs.json         # закріплені командою `workdir` папки запуску тулів (шляхи на цьому ПК, не в git)
├── .claude/skills/lh-tool/  # скіл: створити тул / підключити існуючий скрипт
├── GUIDE.md              # повний посібник користувача
├── README.md             # вітрина для GitHub: можливості, швидкий старт, таблиця тулів
├── docs/screenshot.svg   # знімок TUI для README (генерується через App.save_screenshot)
├── requirements.txt      # залежності лаунчера (textual)
├── tests/                # unittest: test_local_helper.py, test_tui.py, test_<tool>.py
│   └── smoke/            # smoke.ps1 і smoke.sh: наскрізна перевірка lh з «незручними» шляхами
└── tools/
    └── <tool_name>/
        ├── main.py           # точка входу; docstring = опис для `list` і `-help`
        │                     #   (або main.ps1 / main.sh — тул на PowerShell / Bash)
        └── requirements.txt  # опціонально
```

- Вбудовані тули (`tools/`) знаходяться автоматично; зовнішні — через `registry.json`.
  Зовнішні тули живуть поза цим репозиторієм. Їхні файли не редагувати, якщо користувач
  не просив, а `registry.json` руками не правити — для цього є `add`/`remove`.
  Прохання «підключи/додай/опиши цей скрипт» дозволяє дописати в нього опис і привести
  параметри до argparse/`param()`; логіку — лише з окремого дозволу (див. `/lh-tool`).
- Папку, в якій тул завжди запускається, задавати `lh workdir <tool> <папка>` (`--clear` — прибрати),
  а не правкою `workdirs.json`.
- Групи змінювати командами `group`/`ungroup`/`groups rename|delete`, а не правкою `groups.json`.
  Новий тул клади в доречну існуючу групу (`lh new <name> --group <група>`; список — `lh groups`).
  Нову групу створюй лише якщо користувач попросив або жодна існуюча не підходить.
- Ім'я тулу — `snake_case` (`a-z`, `0-9`, `_`) і не може збігатися з командами
  лаунчера: `list`, `info`, `new`, `setup`, `add`, `remove`, `help`, `ui`, `group`, `ungroup`, `groups`,
  `workdir`.
- Тули не імпортують один одного. Якщо щось повторюється в 3+ тулах, це можна
  винести в `tools/_common/` (папки з `_` лаунчер ігнорує), але не раніше.

## Як писати новий тул

1. Створювати через `local_helper new <name>` або вручну за тим самим шаблоном.
2. **Стандартна бібліотека в пріоритеті.** Сторонню залежність брати лише коли вона
   суттєво спрощує задачу; тоді додати її в `tools/<name>/requirements.txt` і виконати `setup`.
3. **CLI через `argparse`** з `prog="local_helper <name>"`, `description=__doc__` і
   `RawDescriptionHelpFormatter`. Без argparse `local_helper <name> -help` не покаже параметри,
   а TUI не побудує форму. TUI отримує опис аргументів, запускаючи скрипт до `parse_args()`
   (`describe_args` у `local_helper.py`), тому до `parse_args()` не можна робити нічого
   важкого чи з побічними ефектами: тільки імпорти, константи і створення парсера.
   Тул не має питати щось через `input()`: у TUI stdin закритий.
4. **Docstring на початку `main.py`**: перший рядок — короткий опис, далі — що саме
   робить тул і 1–3 приклади у формі `local_helper <name> ...`.
5. Файл закінчується `if __name__ == "__main__": sys.exit(main())`, де `main() -> int`.
6. **Шляхи — тільки `pathlib.Path`**. Враховувати пробіли в шляхах (сама ця папка
   має пробіл у назві) і кирилицю в іменах файлів. Відносні шляхи рахуються від cwd
   користувача, а не від папки тулу.
7. **Кодування**: файли завжди відкривати з `encoding="utf-8"` явно.
8. **Безпечність за замовчуванням**: тули, що змінюють, переміщують або видаляють
   файли, мають `--dry-run` і не перезаписують існуючі файли без `--force`.
9. **Помилки**: зрозуміле повідомлення в `stderr` і ненульовий код виходу, без
   traceback для очікуваних ситуацій. Відсутній пакет → підказка `local_helper setup`.
10. Без надмірної архітектури: ніяких класів, конфігів чи логування «на виріст», якщо
    задача вирішується функцією на 50 рядків.

## Тули на PowerShell і Bash

Python — мова за замовчуванням. `.ps1` — коли просять або задача суто Windows-на; `.sh` — лише на
прохання. Створювати `lh new <name> --lang ps1|sh`. Ті самі правила, що й вище (опис з прикладами,
без інтерактиву, `--dry-run`/`--force`, помилки в stderr + код ≠ 0), плюс:

- **`.ps1`**: першим блоком comment-based help (`.SYNOPSIS` — опис для `list`, `.DESCRIPTION`,
  `.PARAMETER` на кожен параметр, `.EXAMPLE`); параметри в `param()` — з нього TUI будує форму
  (`describe_ps1_args` парсить AST, скрипт не виконується): `[switch]` для прапорців (не `[bool]`),
  `[ValidateSet()]` для варіантів, `[Parameter(Mandatory)]`; без `Read-Host`;
  `$ErrorActionPreference = "Stop"` і `[Console]::OutputEncoding = [Text.Encoding]::UTF8`;
  файл у UTF-8 з BOM. Запуск: `pwsh -NoProfile -ExecutionPolicy Bypass -File`, тому масиви з
  командного рядка не розбиваються.
- **`.sh`**: shebang, далі суцільний `#`-коментар (перший рядок — опис, потім параметри й
  приклади); `set -euo pipefail`; лише LF. Форми в TUI немає — аргументи вводяться рядком.

## Перевірка

- Після створення чи зміни тулу запустити `python local_helper.py <name> -help` і хоча б
  один реальний сценарій на тестових даних.
- Тестові та тимчасові файли створювати в тимчасовій папці, а не в репозиторії.
- Після змін у `local_helper.py` запускати `.\.venv\Scripts\python.exe -m unittest discover tests`.
- Після змін у запуску тулів, шляхах чи обгортках (`lh.cmd`, `lh`) — ще й smoke-перевірки:
  `pwsh -File tests\smoke\smoke.ps1` і `bash tests/smoke/smoke.sh` (див. GUIDE.md, розділ 11).
- Формальні тести для тулів пишуться лише коли логіка нетривіальна; кладуться в
  `tests/test_<name>.py`.
